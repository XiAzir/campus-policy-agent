## 主要修复

| 位置 | 原问题/风险 | 修复 |
|---|---|---|
| `db.rs` | 有界同步队列的 `send` 可能阻塞唯一 Tokio 工作线程；队列积压与取消处理不足 | 异步侧 `try_send`，队列满立即返回忙错误；控制消息异步发送；跳过已取消读任务，长检索分批检查取消 |
| `db.rs` | 工作任务 panic 会损坏工作线程可用性；手工事务 panic 后可能残留事务 | 捕获任务 panic；未自动提交状态下回滚；Unicode 审计详情按字符边界截断 |
| `retrieval.rs` / `vectors.rs` | 全量候选、全量得分排序与大读取缓冲使临时内存随分块数扩大 | 每批 512 个候选、固定容量 Top-K、256 KiB 向量工作缓冲；最多缓存 8 个向量文件句柄；仅对最终命中读取元数据；增加有序扫描索引 |
| `vectors.rs` | NPY 头解析宽松、形状/长度溢出及 C/F 布局候选越界行为不一致 | 严格验证版本、dtype、维度、形状、布局、文件长度与有限数值；统一候选去重/排序/越界规则；保留 C/F 布局检索 |
| `archive.rs` / `pkgfmt.rs` | 构造 ZIP 目录后才限额，无法保护解析阶段；仅信任声明大小；逐行分配大量 String | ZIP/ZIP64 结束记录与实际目录条目预检，限制扩展记录；清单限量读取；标准化原文按借用行单遍比对；移动文档 JSON 而非反复复制 |
| `backup.rs` | 恢复依赖声明大小，异常条目与文本可能耗费超出预期的资源；恢复后 TTL 不一致 | 按实际读取量检查恢复条目、清单和文本，保留维护门/原子切换/回滚；恢复后沿用配置 TTL |
| `api` / `text.rs` / `agent.rs` | 极端行号溢出、超长单行、非法范围/历史角色、读取故障被混淆为无证据 | 饱和行号运算、有界原文窗口；统一 JSON 错误；拒绝非法参数；检索故障明确报错，不把失败当作“没有政策” |
| `llm.rs` / `chat.rs` | embedding 响应及收集的模型 parts 缺少实际大小上限；上下文重复分配；SSE 缓冲反复搬移 | 有界流式读取、稳定向量归一化、parts 数量/字节预算、单遍历史裁剪、按偏移消费 SSE；HTTP 重定向禁用；客户端初始化失败不静默回退安全策略 |
| `main.rs` / `auth.rs` | 主机/IPv6 绑定拼接边界；不合法 TTL/密钥配置 | 使用主机与端口元组绑定，验证密钥与 TTL，避免时间运算溢出 |
| 测试与基准生成器 | 干净克隆缺少被忽略的 ZIP 夹具；D1 向量行号跨文档重复、正文行号漏标题 | 从已跟踪合成资料动态构造夹具；修正 D1 行号；新增完整 HTTP 基准，实际走导入/发布而非直接向数据库灌数据 |

检索中间结果的上界不代表数据库总容量固定。允许文档集合、中文词典和 SQLite 等仍有随数据/功能变化的成本；不承诺任意规模资料的总 RSS 都低于本次实测值。新增数据库索引也有磁盘空间代价。

## 明确的新增/收紧边界

| 对象 | 限额或规则 |
|---|---|
| SQLite 单个值/行 | 8 MiB；不是“整个数据库只占 8 MiB” |
| 原文接口窗口 | 最多 201 行且 256 KiB；超长单行/非法 UTF-8 返回错误 |
| 标准化原文 | 4 MiB，并校验实际行数/分块原文一致性 |
| 资料包清单 | 实际读取不超过 8 MiB |
| ZIP 中央目录 | 资料包最多 10002 项、4 MiB；备份最多 100000 项、32 MiB |
| ZIP64 扩展结束记录 | 扩展数据最多 64 KiB；目录实际长度/条目数须与声明一致 |
| ZIP 结构 | 不接收分卷、尾随垃圾和目录不连续的归档；普通 ZIP 与经过验证的 ZIP64 继续支持 |
| 备份清单 | 实际读取不超过 16 MiB；解压条目不得超过声明大小 |
| embedding 响应 | 实际读取最多 1 MiB；维度 1–8192，拒绝 NaN/Inf/零范数 |
| 模型累计 parts | 最多 4096 个、序列化最多 2 MiB；其他已有 SSE/回答限制保留 |
| 数据库工作队列 | 满时返回错误，不阻塞异步线程；读者数 1–8，队列长度 1–1024 |

超限是显式失败，不是静默删证据或截断后继续生成答案。正常前端协议通过现有组件与 API 回归；调用方使用未定义角色/范围模式、超大上下文或特殊 ZIP 结构时，需要处理新的拒绝结果。

## 完整服务内存/性能对照

使用同一批合法合成 ZIP：100 文档、10000 分块、1024 维 float32、5 个资料包，裸向量约 39.1 MiB。两个版本各启一个全新服务进程、各测两次；最终修复版包含最后的 ZIP 补强。每次完整流程为真实管理员登录、HTTP 导入/发布、5 次预热、40 次顺序问答、10 个并发客户端排队问答、20 次原文窗口读取、流式备份下载，结束检查 running/waiting 均为 0。问答必须收到 done/metrics 和非空引用，不把 HTTP 200 当作唯一成功条件。并发客户端沿用原有 Agent 队列，不代表 10 个模型任务同时执行。

模型与 embedding 为独立进程内的 loopback 模拟上游：每个模型调用人为延迟 10ms；反复使用固定政策问题以比较后端检索路径。每次问答包含工具调用与引用，不能代表真实模型回答质量、外网延迟或复杂多轮长上下文。

环境：Linux 6.18.35、x86_64、Intel Xeon Platinum 8370C 2.80GHz、Rust 1.98.1。通过 taskset 在服务启动前绑定一个逻辑 CPU，使全部服务线程继承同一亲和性。执行容器内存限额为 4 GiB，没有对服务施加 1 GiB/512 MiB 硬限制。沙箱 overlay 文件系统出现 fsync I/O 错误，因此两版均在 tmpfs 测临时数据；**没有关闭 SQLite 同步来绕过错误**。

每 10ms 从 `/proc/PID/status` 采样服务进程 RSS，另记录 VmHWM、CPU 时间、FD、线程数。RSS 包含完整 Rust HTTP 服务线程，不含模拟上游、负载客户端、内核页缓存或同机其他服务。短于采样间隔的瞬态峰值可能漏采，不能把表内数值当作 cgroup 总内存或系统峰值。

| 指标 | 原版两次 | 修复版两次 | 两次均值变化 |
|---|---:|---:|---:|
| 启动空闲 RSS（MiB） | 10.11 / 10.16 | 10.31 / 10.16 | +1.0% |
| 预热后 RSS（MiB） | 103.19 / 99.25 | 86.09 / 86.09 | -15.0% |
| 全过程采样峰值 RSS（MiB） | 103.81 / 99.84 | 86.29 / 86.32 | -15.2% |
| 导入/发布采样峰值 RSS（MiB） | 92.34 / 92.64 | 75.13 / 75.11 | -18.8% |

## 复现

以下在 Linux/WSL 中运行，使用隔离合成数据，不需要生产密钥。生成器需要 NumPy；基准脚本本身只用 Python 标准库。

```bash
python -m venv .venv-bench
. .venv-bench/bin/activate
python -m pip install numpy
python scripts/rust/gen_d1.py --dataset d1
(cd backend-rust && cargo build --locked --release --bins)
python scripts/rust/bench_http.py \
  --binary backend-rust/target/release/campus_policy_backend \
  --dataset .local-acceptance/datasets/d1 \
  --output .local-acceptance/repaired-http.json --label repaired
```

在同一机器用 `git worktree add --detach ../campus-policy-baseline b706c4584bc0d29621393972d36f912cfa158e10` 建立基线工作区，进入其 `backend-rust` 编译；仍使用修正后的生成器与同一批 ZIP，用同一个 `bench_http.py` 指向基线二进制。至少重复测量，不混用独立 `bench_d1` 进程指标。
